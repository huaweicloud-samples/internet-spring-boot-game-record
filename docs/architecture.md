# 架构说明

本文说明本实践的组件划分、请求与数据流向，以及各组件之间的依赖关系。

## 组件总览

| 层次 | 组件 | 承担职责 |
|---|---|---|
| 接入 | 弹性公网 IP + 弹性负载均衡（独享型，七层） | 对外统一入口，按轮询分发请求，并以后端健康检查控制流量 |
| 计算 | 弹性云服务器 + 系统服务 | 运行 Java 应用，同时提供页面与接口 |
| 数据 | 云数据库 GeminiDB（兼容接口） | 存储参与者、场次、对局、落子、局面五类记录 |
| 通知 | 消息通知服务 SMN | 发布参与者创建与对局结束事件，支持邮件订阅 |
| 存储 | 对象存储服务 OBS | 存放发布产物 |
| 身份 | 统一身份认证 IAM | 以委托为实例发放运行期临时凭据 |
| 网络 | 虚拟私有云 VPC | 承载子网、安全组与互联网网关 |

## 请求流向

1. 浏览器通过弹性公网 IP 访问负载均衡的 80 端口。
2. 负载均衡按轮询策略把请求转发到后端池中的应用实例。
3. 应用实例在同一次请求内完成业务处理：读取或写入宽表存储，必要时发布通知事件。
4. 负载均衡每 10 秒访问一次 `/api/rules`，连续失败达到阈值后把该实例摘出后端池。

页面与接口由同一个进程提供，因此浏览器访问页面与调用接口同域，不需要跨域放行。跨域仅在把前端单独跑在另一个端口做调试时才需要，此时通过 `CORS_ALLOWED_ORIGINS` 指定允许的来源。

## 数据模型

五类记录各占一张表，均以 `id` 为主键。

| 表 | 主键 | 二级索引 | 说明 |
|---|---|---|---|
| `scorekeep-user` | `id` | 无 | 参与者及其名称 |
| `scorekeep-session` | `id` | 无 | 场次、归属者、参与者集合、包含的对局集合 |
| `scorekeep-game` | `id` | `session-index`（分区键 `session`） | 对局、规则、参与者集合、落子与局面编号列表、起止时间 |
| `scorekeep-move` | `id` | `game-index`（分区键 `game`） | 单次落子的标记与格位 |
| `scorekeep-state` | `id` | `game-index`（分区键 `game`） | 落子后的局面文本与待落子一方 |

二级索引是全字段投影。按场次列出对局、按对局列出落子与局面，都走索引查询而不是全表扫描。

表名前缀由环境变量 `TABLE_PREFIX` 控制，缺省为 `scorekeep`，便于在同一实例上隔离多套环境。

### 表结构的产生方式

应用启动时会执行一次幂等的结构初始化：

1. 逐个查询目标表是否存在。
2. 表不存在时，按主键与二级索引定义建表。
3. 表已存在时，比对其已持有的二级索引，只补齐缺失的部分。

这一步很有必要：只带主键的表即使被自动创建出来，也不会附带二级索引，而按场次或按对局检索恰恰依赖索引。把结构初始化放在服务对外提供流量之前完成，可以让首次部署不需要任何人工准备数据面。

## 数据面接入方式

宽表存储的数据面使用实例自带的数据库账号做静态签名，不使用统一身份认证签发的临时凭据。接入点由实例的负载均衡地址与数据面端口给出（端口随部署形态而定：集群形态为高可用端口 80，单节点形态为 8000），区域标识只参与请求签名，不参与请求路由。

因此有一条重要的边界：绑定在实例上的委托对数据面**不产生授权作用**。委托只用于应用向消息通知服务发布事件。业务写入所需的凭据通过实例上的配置文件提供，文件权限收敛为仅服务账号可读。

## 通知与权限

应用在两处发布事件：创建参与者并随机分配名称时，以及对局进入终局时。发布动作在独立线程中执行，通知服务的响应时延不会传导到接口调用方；发布失败只记录日志，不影响对局主流程。

运行期凭据来自委托：应用从实例元数据服务获取临时凭据后构造通知服务客户端。实例磁盘上不保存任何长期密钥。通知主题与邮件订阅由 Terraform 创建，邮件订阅需要收件人确认后生效。

## 发布与部署

1. 本地构建出可执行包（`src/api/build/libs/scorekeep-api.jar`）。
2. Terraform 把该包上传到对象存储桶，作为发布记录的权威来源。
3. Terraform 经 SSH 把同一个包下发到每台应用实例，写入 `/opt/scorekeep/`。
4. 实例上的系统服务以该包启动应用，并设置为开机自启与异常自动重启。
5. 应用启动后自建表结构，随后负载均衡的健康检查转为通过，实例开始承接流量。

变更应用版本时，更新 `app_revision` 变量即可触发重新下发与重启。

## 可用性边界

- 计算层可以横向扩展：把 `instance_count` 调到 2 至 4 会让所有实例同时注册到后端池，健康检查自动隔离异常实例。
- 数据层为多节点集群，实例内部自带副本与故障切换，应用侧无需感知。
- 应用为无状态设计，同一个场次或对局可以被任意实例处理，不依赖本地会话。
